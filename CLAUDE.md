# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**Tandem** (repo/domain still named "En lice", enlice.eu) — a French-language app that pairs two
people who *disagree* on a curated topic, runs a turn-based async dialogue between them, and has
an LLM score the exchange on dialogue quality (curiosity, constructiveness), not on who is right.

User-facing strings say "Tandem"; the repo, domain, and infra say "En lice" — same product.

## Stack & repo layout

Single **PocketBase** binary is both backend and host, deployed on one Hetzner box at enlice.eu.
No separate API server, no ORM, no test framework in this repo.

```
pb_migrations/   versioned schema, applied automatically on pocketbase start (18 collections)
pb_hooks/        server logic — JSVM (Goja), not Node. *.pb.js register hooks/routes;
                  lib/*.js are required modules with shared helpers
pb_public/       built SPA output (generated by `frontend`'s build — do not hand-edit)
frontend/        Vite + React 18 SPA source, hash router, inline styles (no CSS framework)
scripts/         seed.mjs — seeds topics + fake users with random opinions for testing
deploy/          setup-server.sh (provision a fresh box) + deploy.sh (build, push, restart)
```

Two files are stale root-level leftovers, not the real code: `main.pb.js` and `ui.jsx` at repo
root. The real ones are `pb_hooks/main.pb.js` and `frontend/src/ui.jsx`.

`REVIEW_AND_FIXES.md` and parts of `README.md` describe scoring as a Phase-0 stub and auth as
SSO — both are outdated. Scoring is live (Anthropic API) and auth is plain email/password. Treat
this CLAUDE.md and the actual code as the source of truth over those two docs.

## Commands

```bash
# Local dev — frontend against the live prod backend
cd frontend && npm install
VITE_PB_URL=https://enlice.eu npm run dev

# Build the SPA (outputs into ../pb_public, what PocketBase serves)
cd frontend && npm run build

# Run the backend locally (serves pb_public + runs pb_hooks/pb_migrations from cwd)
./pocketbase serve            # binary must be downloaded separately, not in this repo

# Seed topics + N fake users with random opinions (needs a running PocketBase + superuser)
cd scripts && npm install
PB_URL=http://127.0.0.1:8090 PB_ADMIN_EMAIL=you@example.com PB_ADMIN_PASSWORD=*** \
  SEED_USERS=20 npm run seed

# Deploy: builds the frontend, rsyncs pb_migrations/pb_hooks/pb_public, restarts the service
./deploy/deploy.sh <ssh-target>   # e.g. root@<ip> or an ssh config alias; pb_data is never synced

# Provision a fresh Ubuntu 24.04 box (run once, as root, on the target)
./deploy/setup-server.sh enlice.eu 0.39.2 linux_arm64   # linux_amd64 for CX/CPX servers
```

There is no lint or test command configured in either `frontend/package.json` or
`scripts/package.json`, and no test files exist in the repo.

## Architecture

### PocketBase JSVM gotchas (will waste time if rediscovered)

- **Every `routerAdd`/hook callback is compiled in isolation.** A top-level `function` declared
  in a `.pb.js` file is invisible inside its own route handlers (throws `ReferenceError`). Every
  handler must `require(\`${__hooks}/lib/x.js\`)` *inside the callback body* — that's why small
  helper modules like `lib/scoringExport.js` exist instead of inline functions.
- `e.bindBody()` needs `new DynamicModel({...})`, not a plain object literal — binding into `{}`
  fails with a Go-level `json: Unmarshal(non-pointer ...)` error on this PocketBase version.
- JSON fields read back as a `JSONRaw` wrapper, not a parsed object — plain property access
  silently yields `undefined`. Go through `.getString()` + `JSON.parse()`.
- **Duplicate hook files exist; only some are live.** `pb_hooks/dialogue.js` + `pb_hooks/scoring.js`
  are the real, current ones (required by `main.pb.js`). `pb_hooks/lib/dialogue.js` and
  `pb_hooks/lib/scoring.js` are older near-copies — but `messages.pb.js` still requires
  `lib/dialogue.js` for `onMessage`. Check which path a given caller actually requires before
  editing either version.

### User journey → hook chain

1. **Inscription** (`frontend/src/screens/Inscription.jsx`) — email+password signup via
   `pb.collection('users').create/authWithPassword`, pick a unique pseudonym, accept the charte.
   `pb_hooks/moderation.pb.js` rejects signup at `onRecordCreateRequest('users')` if the email is
   in `banned_emails`.
2. **Opinions** — 1–5 stance per active topic. `pb_hooks/onboarding.pb.js` fires on every
   `opinions` create/update → `lib/onboarding.js recompute()` flips `users.onboarding_complete`
   once every active topic has an answer.
3. **Accueil** — join `matchmaking_queue`. `pb_hooks/matchmaking.pb.js` runs the matcher three
   ways: instantly on queue-join (`onRecordAfterCreateSuccess`), every minute via `cronAdd`, and
   on demand via `POST /api/matcher/run` (superuser only). Matcher logic is
   `pb_hooks/lib/matchmaking.js runMatcher()`: scores every queued pair by clash (max stance
   diff) + shared ground, tiers them, greedily assigns non-conflicting pairs. `CAP = 1` = one
   concurrent dialogue per user (not 5, despite what some docs say). `DURATION_DAYS = 7` also
   lives there. "Never re-match" is enforced by a UNIQUE index on `dialogues.pair_key`
   (`[idA,idB].sort().join('_')`) — that index is the actual atomic guard; the in-code
   `pairExists`/`activeCount` pre-checks in `openDialogue()` only reduce (not eliminate) a
   concurrent-match race.
4. **Dialogue** — turn-based, realtime via PocketBase subscriptions. `pb_hooks/messages.pb.js`
   flips `dialogues.current_turn` and notifies the other participant on every non-prompt message
   (`lib/dialogue.js onMessage`). A dialogue ends three ways, all converging on
   `pb_hooks/main.pb.js`'s `onRecordAfterUpdateSuccess('dialogues')` when `status` becomes
   `'ended'`: (a) the 7-day `dialogue_expiry` cron (`lib/dialogue.js expireDialogues`), (b) the
   user hitting `POST /api/dialogue/{id}/leave` (`lib/dialogue.js leaveDialogue`), (c) an admin
   force-ending it. That hook is the single entry point that triggers scoring
   (`lib/dialogue.js runScoring`) — it checks `dialogue_participant_scores` for an existing row
   first to avoid double-scoring, since saving `collective_criteria` re-triggers the same hook.
   A ⚑ button writes to the `reports` collection directly from the client
   (`Dialogue.jsx flag()`) — there is currently no admin UI that reads `reports` or turns them
   into `sanctions`; both collections exist in the schema but nothing in `pb_hooks` touches them.
5. **Scoring** (`pb_hooks/scoring.js` → `pb_hooks/lib/scoringEngine.js`) — an 8-criterion French
   rubric (6 individual: respect, clarté, argumentation, nuance, écoute active, fair play; 2
   collective: clarification mutuelle, construction du dialogue), each 0–5 with a justification
   and confidence. Prompt and model are **not hardcoded**: `app_settings.scoring_prompt`
   overrides `DEFAULT_PROMPT` if set, and whichever `scoring_apis` row has `is_default = true`
   picks the model (falls back to Anthropic `claude-haiku-4-5-20251001`). The API key itself is
   never stored — only an env var *name* (e.g. `ANTHROPIC_API_KEY`) is stored in the
   `scoring_apis` row, read via `$os.getenv()` at call time. `scoringEngine.js` also supports an
   OpenAI/Mistral-compatible chat-completions path (same wire format, different default
   endpoint/model).
6. **Bilan** — radar charts (Recharts) of the 6 individual + 2 collective scores; polls briefly
   after a dialogue ends since scoring is async.
7. **Classement** — reads `global_scores`, sorted by `total`. **Nothing in `pb_hooks` ever
   writes to `weekly_scores` or `global_scores`** — no aggregation cron exists — so this screen
   is currently always empty in practice, regardless of how much scoring has happened.

### Admin console (`/#/admin`, `frontend/src/screens/Admin.jsx`, superuser token login)

Backed by `pb_hooks/admin.pb.js` (stats dashboard, matchmaking toggle, force-end dialogues,
toggle user active, match-preview/match-force between two specific users, read any dialogue's
messages) and `pb_hooks/admin_scoring.pb.js` (the **scoring lab**: edit/reset the production
prompt, manage `scoring_apis` rows and which is default, re-run scoring on an already-ended
dialogue N times to measure score stability, export results to CSV, or push to a Google Sheet via
OAuth refresh-token flow). Every route in both files independently re-requires its `lib/` helpers
per the JSVM isolation gotcha above. Scoring-lab runs write only to `scoring_test_runs` — they
never touch a user's real `dialogue_participant_scores`.

### Frontend conventions

- All user-visible copy lives in `frontend/src/copy.js` (exported as `COPY`) — edit there, not
  inline in JSX, when changing wording.
- `frontend/src/theme.js` (`KL` token set) + `frontend/src/ui.jsx` (Screen, Card, Button, Pill,
  Meter, Avatar, Field, Scale, Mono) are the whole design system — no CSS framework, no
  stylesheet files, styles are inline objects built from `KL` tokens.
- `frontend/src/auth.js` is a thin reactive wrapper over `pb.authStore`; `frontend/src/pb.js`
  points the PocketBase client at `VITE_PB_URL` or same-origin in prod.
- Routing is a hash router (`App.jsx`) gated by a `<Gate>` component that redirects based on
  `user.pseudonym` / `guidelines_accepted_at` / `is_active` / `onboarding_complete`, in that
  order — read this gate logic before changing anything about the onboarding sequence, since it
  is the actual source of truth for which screen a user lands on.

## Deploy notes

The prod server only runs the `pocketbase` binary (no Node/npm/git there) — it's a pure deploy
target, never a place to hand-edit code. `deploy/deploy.sh` rsyncs `pb_migrations/`, `pb_hooks/`,
and a freshly-built `pb_public/` to `/opt/pocketbase/` and restarts the systemd service; anything
changed only on the server gets clobbered on the next deploy. `pb_data` (the actual database) is
intentionally never synced either direction.

PocketBase has no encryption at rest, and this app stores users' political opinions — `pb_data`
should live on an encrypted volume before any real-user launch, per the README's security note.
